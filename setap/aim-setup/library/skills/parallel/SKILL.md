# parallel · вторая сессия в своей копии проекта

**Когда запускать:** человек просит вторую сессию, спрашивает про worktree или «как делать два дела сразу». Или план утверждён, в нём два куска трогают разные файлы (облик и логика, бот и страница), а в `about-me.md` на дело два часа в день и больше – тогда одной строкой предложи: «облик и логику можно вести в двух сессиях параллельно – завести?». Человек раз отказался – сам больше не предлагай. Ставить скилл не нужно: читай этот файл из `library/skills/parallel/`.

**Зачем:** две сессии в одной папке проекта пишут друг поверх друга. У каждой должна быть своя копия проекта. Копию заводит агент; скиллы, `context/` и `PLAN.md` у обеих сессий общие, потому что обе открыты в папке набора.

**Ничего не ломать:** всё здесь по желанию. Человек отказался – работайте одной сессией, как раньше. Уже идущую работу не переносим и не переименовываем: копия появляется рядом, основная `project/` остаётся на месте.

## 1 · git

Проверь: `git -C project rev-parse --show-toplevel`.

- **Git нет** (ошибка или человек не ставил его в шаге 0 `build`) – объясни и спроси одним вопросом:
  «git – журнал версий проекта: после каждого рабочего шага я сохраняю снимок, и если что-то сломается, вернёмся к любому из них. Ещё он умеет держать вторую рабочую копию проекта – worktree – на своей ветке: вторая сессия правит копию, первая – основную папку, друг другу не мешают, а потом я сливаю копию обратно. После этого в проекте можно вести несколько сессий сразу – каждой свою копию. Завести git?»
  «Да» – пройди «точку возврата» из шага 0 `build` целиком: проверка на чужой репозиторий, `git init` в `project/`, `.gitignore`, проверка ключей, автор, пробный коммит. «Нет» – одна сессия, дальше не идём.
- **Ответ – не та же папка, что `$(cd project && pwd -P)`** (проект лежит внутри чужого репозитория) – копию не заводи: «проект лежит внутри другого репозитория – вторую копию тут не заведу, работаем одной сессией».
- **Git есть, а коммитов нет** (`git -C project rev-parse HEAD` – ошибка) – сначала первый коммит: копию заводят от него.
- **Git есть** – одной строкой объясни, что такое worktree (вторая половина объяснения выше), и переходи к шагу 2.

## 2 · копия

1. **Задача второй сессии.** Не названа – один вопрос: «что отдаём второй сессии?» Задача трогает другие файлы, чем текущий шаг основной сессии; пересекаются – скажи, что одна из сессий будет ждать, и предложи разделить иначе.
2. **Точка возврата.** `git -C project status --short` не пусто – сначала коммит в основной папке.
3. **Копия.** Имя – одно короткое слово латиницей по задаче (`design`, `bot`, `data`); оно же имя ветки. Ветка или папка с таким именем уже есть – возьми другое (`design2`). Из папки набора:
   ```
   git -C project worktree add "$(pwd)/worktrees/<имя>" -b <имя>
   ```
   Копия ляжет в `worktrees/<имя>/` в папке набора. В копии есть всё из последнего коммита – и нет того, что git не хранит:
   - ключи: файлы `project/.env` и `project/.env.*` есть – скопируй их в копию (`cp project/.env* worktrees/<имя>/`); содержимое не открывай. Ключ, положенный позже скриптом `put-key`, ляжет только в `project/.env` – скопируй его во вторую копию так же;
   - пакеты: в проекте есть `package.json` и `package-lock.json` – `npm ci --prefix worktrees/<имя>`: это те же пакеты, что уже стоят, – человеку одной строкой. Lock-файла нет – это новая установка: спроси «да»;
   - картинки и файлы, которые лежат вне git (`docs/research/sources/`), – в копии их нет; нужны второй сессии – скажи.
4. **Запись.** `context/parallel.md`, строка на копию: дата, имя, папка, ветка, задача, порт копии (свободный и не как у основной, например 5792). Порт основной – в `project/.aim/`.
5. **Человеку** – одним сообщением:
   «Копия готова: `worktrees/<имя>/`. Открой новую сессию агента в этой же папке набора (в приложении Claude – вкладка Code, новая сессия, та же папка; галочку «worktree» не ставь, копию я уже завёл). Напиши в ней: «работаешь в копии worktrees/<имя>: <задача>». Здесь я продолжаю <шаг плана>. Когда вторая скажет «готово», напиши мне «слей копию <имя>».»

## 3 · вторая сессия

Тебе написали «работаешь в копии `worktrees/<имя>`» – ты вторая сессия. Прочитай `context/` как в `build` и строку своей копии в `context/parallel.md`. Вторая сессия зависла или кончился лимит – новая начинает той же фразой; просто «продолжаем» при открытой копии – вопрос из `build`.

- **Твоя папка – копия.** Везде, где в скиллах написано `project/`, у тебя `worktrees/<имя>/`: `git -C worktrees/<имя>`, номера серверов в `worktrees/<имя>/.aim/`, сервер – на порту копии. В `project/` основной сессии не пиши. Снимки по `look` – с профилем `<tmp>/look-profile-<имя>`, `browser` – с сеансом `--session <имя-проекта>-<имя>`: профиль и сеанс основной сессии заняты, чужие окна не закрывай.
- **Общее не правь.** `context/` (вместе с `lessons.md`) и `PLAN.md` ведёт основная сессия; ты их читаешь. Документацию проекта в копии – `README.md`, `docs/PROJECT.md`, `docs/DECISIONS.md` – тоже не трогай: обе сессии допишут в конец одних файлов, и слияние упрётся в конфликт. Уроки, решения и что поменять в документации – строками в сообщение «готово», основная запишет. Исключение – строка в `context/kit-feedback.md`.
- **Пункты `build`, которые у тебя другие.** Отметка в `PLAN.md` после шага, сверка «конец вечера» из `AGENTS.md` и `docs-updater` – у тебя это три строки в «готово»; в общие файлы не пиши. Серверы и браузеры гаси свои – номерами из `worktrees/<имя>/.aim/`.
- **Облик.** Твоя задача в `context/parallel.md` – облик: `context/taste.md` правишь ты, основная сессия его до слияния не трогает (и не правит экраны). Задача другая – `taste.md` только читаешь.
- **Коммиты** – в свою ветку после каждого рабочего куска. Проверка ключей общая с основной папкой и срабатывает сама; у человека свои проверки коммитов (шаг 0 `build`) – перед коммитом `bash checks/scan-keys.sh --staged worktrees/<имя>`.
- **Без «да» не делай:** выкладку, туннели, установку новых пакетов, слияние.
- **Готово** – проверь результат по `look` (или тестами), закоммить всё, погаси свой сервер номером из `worktrees/<имя>/.aim/` и скажи человеку: «копия готова – напиши основной сессии «слей копию <имя>»». Что сделано и что вышло иначе – тремя строками в том же сообщении: основная перенесёт это в `PLAN.md`.

## 4 · слияние – в основной сессии

1. `git -C worktrees/<имя> status --short` не пусто – вторая сессия ещё работает или не закоммитила: «во второй копии есть незакоммиченное – попроси её закончить и закоммитить».
2. Своё – закоммить. Потом из папки набора: `git -C project merge --no-edit <имя>`.
3. **Конфликт** (обе сессии правили одно место) – не решай молча. Покажи человеку файлы и места одной-двумя строками и спроси, что оставить; сводишь по его слову. Не уверен – `git -C project merge --abort`: всё вернётся как было до слияния.
4. После слияния – проверка по `look` или тестами, отметка в `PLAN.md` (что сделала вторая сессия), строка в `context/parallel.md`: «слита <дата>».
5. **Убрать копию** – после «да» человека: «копия слита – убрать папку `worktrees/<имя>/`?». Вторая сессия закрыта; её сервер, если жив, гаси только номером из `worktrees/<имя>/.aim/`. Потом:
   ```
   git -C project worktree remove "$(pwd)/worktrees/<имя>"
   git -C project branch -d <имя>
   ```
   `worktree remove` отказался – прочитай текст ошибки: незакоммиченное в копии – покажи человеку, что именно; файл занят (на Windows – живой сервер или открытая папка) – погаси сервер копии, попроси закрыть вторую сессию и повтори. `--force` не используй.
6. **Отказаться от копии** – человек передумал, сливать не будем: «в ветке <имя> N коммитов – они пропадут; убрать?». После «да» – `worktree remove`, как выше, и `git -C project branch -D <имя>`; строка в `context/parallel.md`: «убрана без слияния <дата>».

## чего нельзя

- две сессии в одной папке проекта – ни в `project/`, ни в одной копии;
- сливать копию, пока вторая сессия в ней работает;
- копию внутри `project/` или вне папки набора – вторая сессия не увидит скиллов и `context/`;
- удалять копию или ветку без «да» и с несохранённой работой;
- выкладывать и поднимать туннель из копии: в ней нет привязки к площадке (`.vercel/` и такие папки git не хранит), выкладка заведёт второй проект. Выкладка – только из `project/` после слияния;
- переносить набор в новую папку с открытыми копиями: сначала слей или убери их (после переноса копия смотрит в старую папку; если уже перенесено – `git -C project worktree repair`).
