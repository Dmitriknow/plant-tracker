# build · план и сборка, недели 2–4

**Когда запускать:** после интервью, когда человек пишет «продолжаем», «дальше», «поехали», «го», «погнали». Вход в новой сессии, по порядку:

1. Прочитай `context/about-me.md`, `context/vision.md`, `context/project.md`, `context/kit.md` и, если есть, `context/self.md`, `context/boundaries.md`, `context/taste.md`, `context/lessons.md`, `context/parallel.md` – между сессиями ты их не помнишь. Правила из `lessons.md` – такие же правила, как в `AGENTS.md`.
1а. Нет `context/boundaries.md` (работа перенесена из прошлой версии) – один раз задай вопрос 14 из `start` и запиши файл. У шагов `PLAN.md` метки вечеров (`[чт]`, `[пт]`) – предложи переставить оставшиеся шаги по неделям и после «да» обнови.
2. Нет `context/kit.md` – интервью не закончено: продолжи `start` с того места, которого ещё нет в `context/`.
3. В `context/parallel.md` есть неслитая копия, а человек написал просто «продолжаем» – один вопрос: «это основная сессия или вторая, в копии <имя>?»
4. В `PLAN.md` есть строка `**Утверждён:**` – начни вечер одной строкой: где мы, какой шаг этой недели по `date`, что заработает к концу вечера; ответа не жди, берись за шаг. Строки нет – шаг 1. План из прошлой версии набора (строки нет, у шагов уже стоят ✓) – утверждён раньше: допиши `**Утверждён:** <дата> – утверждён раньше` и иди дальше.

**Что должно получиться:** работающее дело в `project/`, собранное по утвержденному плану, с точками возврата, проверками и вторым взглядом.

## шаг 0 · комплект и точка возврата

- Проверь комплект из `context/kit.md`: скиллы видны (`.claude/skills/` в Claude Code, `.agents/skills/` в Codex/Cursor/Antigravity, `.opencode/skill/` в opencode)? Не видно (продолжаем в старой сессии) – открой нужный `SKILL.md` в папке своего агента (папки нет – в `library/skills/<имя>/`) и работай по нему; человеку одной строкой: «инструменты не подхватились, работаю по файлам».
- В `context/kit.md` комплект есть, а в папках скиллов его нет (человек перенёс работу в новую версию набора) – поставь его заново из `library/` по списку в `kit.md`, как в `start`: скиллы во все три папки, агентов – в `.claude/agents/`. Комплект уже согласован – второго «да» не нужно; человеку одной строкой: «перенёс твой комплект в новую версию набора».
  - номера в `project/.aim/` приехали из старой папки. Живой процесс по такому номеру – либо сервер старой копии (отдаёт старые файлы), либо уже чужая программа (после перезагрузки номера раздаются заново). Гаси, только если это твой сервер или туннель, – по проверке номера из `look` («перед запуском»). Не твой – не трогай. В любом случае сотри `.pid` и поднимай заново. Порт занят и после этого – закрой старую сессию агента: «в старой папке ещё работает агент – закрой его, чтобы он не писал рядом».
- **Инструменты на машине** – до первого шага, без установки:
  - git: на маке сначала `xcode-select -p`. Нет – первый вызов `git` откроет окно установки инструментов разработчика; скажи об этом заранее: «нажми «Установить», это минут десять». Windows – `git --version`; нет – одна команда человеку: `winget install --id Git.Git -e` (в нём же bash для проверок ключей); после установки – закрыть и открыть агента.
  - Node, если дело на нём (`node -v`, `npm -v`). Нет – одна команда человеку: мак – установщик LTS с nodejs.org; Windows – `winget install OpenJS.NodeJS.LTS`. Ставит человек сам – установщик спрашивает пароль. После установки – закрыть и открыть агента: старая сессия новую программу не видит.
  - `npm install -g` и `sudo` не используй: пакеты – в проект (`npm install -D …`), запуск – из `node_modules/.bin`. Одно исключение – `agent-browser` по скиллу `browser`, после «да».
- **Свой проект.** `project` – ссылка (`test -L project`; PowerShell – `(Get-Item project).LinkType`) – точку возврата настраивай по `library/skills/own-project/SKILL.md`, шаг 3: `git init`, новый `.gitignore` и замена проверок в чужом репозитории запрещены. Следующие пункты про git – для нового проекта.
- Точка возврата: сначала проверь `git remote -v` – папка внутри чужого репозитория (например, клона) – туда не коммить.
- Если git свой – он живёт внутри `project/`: `git init` и первый коммит там, в корне стартера ничего не коммить (рядом лежат `context/` и файлы сетапа).
  - сразу заведи `project/.gitignore`: `.env`, `.env.*`, `node_modules/`, `dist/`, `*.log`, `.DS_Store`, `.aim/` (номер и лог своего сервера, см. `look`) – корневой `.gitignore` стартера на проект не действует; `dist/` – собранная копия, она пересобирается командой и в историю не идёт;
  - поставь проверку секретов. Сначала узнай, откуда git берёт проверки: `git -C project rev-parse --git-path hooks`. Ответ `.git/hooks` – скопируй `checks/scan-keys.sh` в `project/.git/hooks/pre-commit` и сделай исполняемым: коммит с ключом не пройдёт. Хук там уже есть и отличается от `checks/scan-keys.sh` (`cmp`): первая строка комментария совпадает с `checks/scan-keys.sh` – скопируй заново, это проверка из прошлой версии набора; не совпадает – это чужой хук, его не трогай и гоняй проверку сам перед каждым коммитом, как ниже. Ответ – другая папка (у человека свои общие проверки, `core.hooksPath`) – туда не пиши и настройку не меняй: хук в `.git/hooks` git там не запустит. Человеку одной строкой: «у тебя свои проверки коммитов – мою туда не ставлю, гоняю её сам перед каждым коммитом», – и перед каждым коммитом `bash checks/scan-keys.sh --staged project` – проверяет то, что уходит в коммит;
  - автор коммитов: `git config user.name` или `git config user.email` пусто – поставь недостающее только в `project/`: `git config user.name "<имя из about-me без пометки «(логин)»>"` и `git config user.email "<логин>@local"`; человеку одной строкой: «git не знал твоего имени – записал в этом проекте; почту для GitHub спрошу, если будем выкладывать». Подставлять чужое имя (`-c user.name=…`) – нельзя;
  - сразу пробный коммит: хук не сработал (например, Windows без bash) – сними его, скажи одной строкой и продолжай;
  - после каждого рабочего шага – коммит с короткой подписью («работает форма записи»).
- Человек не стал ставить git – скажи одной строкой, что точек возврата не будет, и продолжай. Ничего не устанавливай без разрешения.
- Стоит `browser` и ты нашёл для него путь к браузеру (`--executable-path`) – запиши строкой в `context/kit.md` сразу: следующая сессия его не вспомнит.

## облик – до первого экрана

У дела есть экран, а `context/taste.md` ещё нет – до первого видимого экрана выбери облик вместе с человеком. Описать вкус словами умеют немногие, а выбрать из показанного может каждый. Экрана нет (бот в чате, скрипт) – `taste.md` не заводи: тон остаётся в разделе «Облик» в `project.md`.

**Готовый стиль.** Человек назвал стиль, который можно открыть, – свой сайт, дизайн-систему, бренд-гайд, своё приложение: направлений не собирай. Стиль собран в Claude Design – попроси человека выгрузить страницу или дизайн-систему файлами в `project/docs/references/` и снимай облик с файлов. Сними облик с него – шрифты, палитру, формы, тон текстов – с открытых страниц и из файлов, которые человек дал в `project/docs/references/`; стиль лежит в папке на компьютере – назови её и спроси разрешение (правило 5). Запиши `taste.md` по шаблону ниже (в строке «Направление» – «готовый стиль: <источник>», файла направления нет), свои выводы пометь «я предположил», собери по нему первый экран, проверь его по `look` и покажи ссылкой с одним вопросом: «похоже на твоё?». Не похоже – поправь по ответу; второй раз мимо – предложи два направления (шаг 1).

Готового стиля нет, экраны уже есть, а `taste.md` нет – сборку не останавливай. Одним вопросом: «зафиксирую облик по тому, что уже получилось, или соберу два-три направления на выбор?» Запиши `taste.md` по ответу, добавь строку в `PLAN.md` и скажи человеку.

**Выбор референсов.** Облик собирается для этого дела и его главного экрана; общий вкус человека здесь материал. Перед пунктом 1: в `project/docs/references/` больше трёх картинок или стилей, они тянут в разные стороны (шрифты, палитры, жанры), а человек ещё не сказал, какие из них про это дело, – спроси одним вопросом: «какие два-три из них ближе всего к этому делу?» Что взято из каждого, пиши в подписях к направлениям. Смесь без выбора модель усредняет – выходит шаблон.

**Картинки экранов.** Твой агент умеет генерировать картинки (например, Codex) – одной строкой предложи начать с них: 2–3 картинки главного экрана по тем же материалам, человек выбирает одну. Выбранную положи в `project/docs/taste/` и собери по ней направление в HTML (пункт 1, одно направление вместо трёх), дальше – как обычно. Генерировать картинки агент не умеет (Claude Code) – одной строкой предложи сделать их человеку: дай короткое описание главного экрана для ChatGPT или Gemini, открой ему папку `project/docs/taste/` (мак – `open "<полный путь>"`, Windows – `explorer "<полный путь>"`; не открылась – дай путь) и попроси перетащить туда 2–3 картинки. Не хочет – сразу направления в HTML.

1. **Два-три направления.** Собери из раздела «Облик» в `project.md`, «сделано хорошо» из `about-me.md` и картинок в `project/docs/references/`. Раздела «Облик» нет или в нём «не сказано» – бери референсы и «сделано хорошо»; нет и их – три заведомо разных направления: выбор покажет вкус. Направления заметно разные: шрифты, палитра, плотность, формы. Каждое – один и тот же главный экран дела, статичный, с настоящими текстами дела, без «Lorem ipsum» и «Добро пожаловать». Файлы – `project/docs/taste/a.html`, `b.html`, `c.html`. Времени в неделю пять часов и меньше (`about-me.md`) – два направления. Выбранное направление не выбрасывай: оно становится основой первого экрана.
2. **Мимо шаблона и сырого.** Прогони направления через `look` – один проход и по снимку на направление: слабые места поправь, признаки шаблона сверь по правилу из `look`.
3. **Показ.** Ссылкой по `look`, сервер – по рецепту `look` («сервер – свой, по номеру процесса»), номер и лог в `project/.aim/`, раздаёт только папку направлений: `python3 -m http.server <порт> --bind 127.0.0.1 --directory project/docs/taste`, ссылки `/a.html`, `/b.html`, `/c.html`. На Windows сначала `py -3 --version` или `python --version` и подставь рабочую команду; Python нет – не ставь его: открой файлы человеку (`explorer "<путь к a.html>"`) и покажи снимками; к каждому направлению – одна строка: что взято из референсов и слов человека. Вопрос: «Какое ближе – или что взять из разных?» В том же сообщении – одной строкой: «это стартовая точка: дизайн доводим по ходу, экран за экраном». После выбора погаси этот сервер своим номером.
4. **Мимо все** – спроси одним вопросом, что именно не так, и покажи ещё один раунд (при пяти часах в неделю и меньше – без раунда). Дальше бери ближайшее и доводи по ходу.
5. **`context/taste.md`** – запиши выбранное:

```markdown
# Облик
- Направление: <одна строка; файл – `project/docs/taste/<выбранный>.html`>
- Шрифты: <названия и роли: заголовки, текст, цифры>
- Палитра: <роли и коды: фон, текст, акцент, линии>
- Плотность и сетка: <воздух или плотно; ширина колонки; выравнивание>
- Формы: <углы, линии, тени – какие есть и каких нет>
- Тон текстов: <как звучат надписи и кнопки>
- Делаем: <2–4 приёма>
- Не делаем: <из «не похоже на» и отброшенного при выборе>
```

Дальше каждый экран собирается по `taste.md`. Человек меняет вкус по ходу – сначала строка в `taste.md`, потом код. Облик ведёт вторая сессия (`context/parallel.md`) – `taste.md` и экраны до слияния не трогай.

**Лист экранов.** Экранов два и больше (или один экран с тремя и больше состояниями: пусто, загрузка, ошибка, готово), и главное на них работает – вместо другого вопроса в конце отчёта шага предложи собрать лист: все экраны и элементы дела (кнопки, карточки, окна, состояния) на одной странице, которую открывает сервер самого дела, с теми же стилями и компонентами. Файл положи туда, где его видит сервер дела (для статичного дела – `project/site/sheet.html`, для сборки – страница рядом с входной: сборка её не берёт, если её нет во входах), и пометь строкой в `PLAN.md`. У каждого элемента на листе – номер: буква экрана и цифра (А1, А2, Б1), чтобы человек говорил «А2 крупнее» и не описывал словами. Сомневаешься между двумя решениями – покажи оба рядом под одним номером: «В3-а или В3-б?». Проверь лист по `look`, покажи ссылкой. Человек смотрит лист целиком и говорит, что поменять; правки – сначала в `taste.md`, потом в код, потом лист заново.

## шаг 2 · сборка по шагам

- У дела есть экран, а `context/taste.md` нет – сначала «облик» (выше).
- **Свой проект** (`project` – ссылка) – прогоняй сценарий из «Что уже есть» после каждого шага; правила сборки – `library/skills/own-project/SKILL.md`.

Страница уже в корне – перед первым адресом шире `localhost` (wi-fi, туннель, выкладка) перенеси её файлы в `project/site/` (`git -C project mv`, коммит) и скажи одной строкой.

- Технический вопрос (сколько картинок принимает один вызов, сколько стоит, сколько займёт) – выясни сам по документации сервиса; лимит, которого в документации нет, проверь на заглушке или одним живым вызовом по правилу платных вызовов из `AGENTS.md`, если ключ уже есть. Человека спрашивай только о том, что знает он: что ему нужно, как должно ощущаться, что он видит у себя.
- Файл, который человек положил или назвал (референс, данные, заметка), – его выбор: по дате изменения не отбрасывай и «свежих нет» не говори. Не нашёл файл – так и скажи и спроси, где он.
- Визуальное – перед показом прогони `look`: посмотри сам, как это выглядит; нажатия и ошибки страницы – `browser`, если стоит. Стоит ли – смотри в `context/kit.md`: стоит – нажимаешь и проверяешь ты, человека об этом не проси.
- Показываешь человеку – подними сервер сам и дай ссылку (`look`, «показ ссылкой»); «запусти у себя …» – не показ.
- Серверы и браузеры гаси только своим номером процесса, никогда по имени (`pkill`, `killall`) – у человека закроются его окна и чужие проекты.
- Ключ в `.env` кладёт человек сам командой из `AGENTS.md` (`checks/put-key.sh`, полный путь в кавычках), ты файл не читаешь. Скрипт пишет в `project/.env` – значит, `package.json` и сервер живут прямо в `project/`. Заготовку (`npm create …`) создавай во временной папке `project/.aim/scaffold` и перенеси файлы в `project/`; сам `project/` создателем не перезаписывай. Человек сказал «положил» – перезапусти свой сервер его номером и проверь, что ключ виден (например, ответ сервера «ключ есть»). Не виден – сначала проверь, из какой папки сервер читает `.env`, и только потом проси человека повторить.
- Картинки: референс пришёл в чат – следующая сессия его не увидит. Рядом с картинкой виден путь к файлу (в Claude Code – строка `[Image source: …]` или `[Image: source: …]`) – сразу скопируй файл в `project/docs/references/`: временная папка живёт недолго. Пути нет – файла у тебя нет. В обоих случаях запиши словами в `project/docs/references/README.md`, что на картинке и что из неё берём (палитра, свет, форма, шрифт), и покажи человеку одной строкой. Картинку читай один раз, копией в 1200 точек по длинной стороне (мак: `sips -s format jpeg -Z 1200 "<файл>" --out "<tmp>/ref.jpg"`; Windows – уменьшить нечем, прочти один раз как есть); дальше работай по описанию в `README.md`, картинку не перечитывай. Скопировал файл – добавь: «картинка лежит в `project/docs/references/` и поедет в git проекта; личное – скажи, уберу». Файл нужен коду (текстура, иконка, фото), а пути не было – открой человеку папку (`open "<путь>"` на маке, `explorer "<путь>"` на Windows) и попроси перетащить файл туда. Снимок экрана при проверке читай, когда надо увидеть облик; положение, текст, углы, состояние – через `eval` и `get text` (`browser`). Каждая прочитанная картинка остаётся в переписке навсегда.
- Правишь то, что уже работало, – сначала коммит: точка возврата должна откатываться одной командой.
- Стоит `update-docs` – в своём проекте существующие README и `docs/` дополняй, новые файлы заводи только после «да». Иначе до первого шага заведи `project/README.md`, `project/docs/PROJECT.md` и `project/docs/DECISIONS.md` по шаблонам: цель, границы, первые решения из плана; запуск заполнится после первого рабочего шага.

После каждого шага:

1. **Самопроверка.** Запусти, открой или прогони то, что сделал, по главному сценарию.
2. **Не показывай сырое.** Найди 2–3 слабых места (края, ошибки, непонятные надписи) и поправь. У шага есть экран – сверка с требованиями из `look`: каждое требование человека ✓ или названо.
3. **Короткий отчет.** Что сделал; ссылка, по которой посмотреть (сервер поднят тобой); что не проверил. Чего агент проверить не может – звук, микрофон, касания на живом телефоне – «○ не могу проверить» и просьба к человеку. След – вывод команды, ответ и код, скриншот (`look`) или словами человека: «открой и скажи, что видишь» – в отчете так и пиши, кто проверял: агент или человек.
4. **План.** Отметь шаг в `PLAN.md`, распиши пункты следующего (`make-plan`, «показ человеку и ведение») и назови их человеку одной строкой.
5. **Коммит** (если git) – короткая подпись.
6. **Документация** (если стоит `update-docs`): шаг изменил устройство или запуск – обнови паспорт и README; решение – строкой в `project/docs/DECISIONS.md`.

Пока в `PLAN.md` есть нерешенные шаги, человеку сообщается статус; слово «готово» – для конца. «Готово» – только со следом проверки.

Для визуального дела: облик выбран до первого экрана, а внутри шага сначала работает и понятно, потом доводка. Доводи по `context/taste.md`; свои представления и стиль по умолчанию сюда не идут.

## сверка на шагах

Работать можно сразу, по `SKILL.md`; перезапуск не нужен. Папка уже есть – не перезаписывай: работай по её `SKILL.md`.
- Новая задача пришла одной строкой, шаг понятен только в общих словах или человек просит «расспроси меня» – `grill-me`: сначала вопросы и пересказ, работа после «да».
- Каждое добавление – строкой в `context/kit.md`: что добавили и почему.
- Свои скиллы человека – раньше библиотеки: есть у него инструмент под нужду – используй его.
- Чего нет ни у него, ни в библиотеке – скажи прямо и предложи вариант; ничего не устанавливай без «да».

## на телефоне

`localhost` с телефона не открывается, а микрофон, камера и звук в браузере телефона работают только по `https`. По порядку:

1. **Хватает компьютера.** Дело можно проверить в браузере на компьютере (на `localhost` микрофон работает и без `https`) – проверяй там, телефон оставь на выкладку.
2. **Та же домашняя wi-fi, без микрофона и камеры** – сервер, открытый в домашнюю сеть, по правилу `look` (с вопросом).
3. **Нужны микрофон, камера или другая сеть** – одно из двух, оба жёлтые, с вопросом:
   - **черновая выкладка** по `deploy-verify` – адрес черновика, не «живой»; если человек уже пользуется площадкой;
   - **временный туннель:** `cloudflared tunnel --url http://localhost:<порт>` – без аккаунта, адрес вида `https://….trycloudflare.com`. Нет `cloudflared` – мак с Homebrew (`command -v brew`): `brew install cloudflared` – ставит человек; без Homebrew – после «да» скачай архив под его систему со страницы `github.com/cloudflare/cloudflared/releases` в `project/.aim/bin/`; Windows: `winget install Cloudflare.cloudflared`.
   - Перед туннелем: Vite пускает чужие адреса только по списку – добавь в `vite.config` `server: { allowedHosts: ['.trycloudflare.com'] }` (для `vite preview` – `preview.allowedHosts`). Проверь, что сервер не раздаёт личное, – проверкой из `look` («адрес шире localhost»).
   - Запуск – в фоне по рецепту сервера из `look`: `(exec cloudflared tunnel --url http://localhost:<порт> > project/.aim/tunnel.log 2>&1) & echo $! > project/.aim/tunnel.pid; echo cloudflared > project/.aim/tunnel.cmd` (скачанный – полным путём из `project/.aim/bin/`); адрес – из лога. Сначала одной строкой: «страница будет открыта всем, у кого есть ссылка; если ключ работает на сервере – чужой может тратить твои деньги; гашу сразу после проверки». После показа – погаси своим номером.

## финал

Когда план выполнен или человек доволен результатом («меня устраивает» – законный финал):

- **второй взгляд на результат** – `second-look`: скажи «минуту, второй агент посмотрит, что получилось», найденное поправь (один проход), человеку переведи одной строкой;
- покажи короткий итог: что работает и как проверить; отдельной строкой след – «проверено: прогон ✓ · взгляд ✓ · второй взгляд ✓ · документация ✓» (три состояния: ✓ проверено, ○ не проверяли, ✗ не прошло; честно; чего не ставили – не пишем);
- скажи: дальше выпуск – прогон, выкладка (если выкладываем), уроки и карточка для демо-дня 07.12; «напиши "сдаю"».

- тащить в сборку пункты из «потом»

- оставлять документацию неактуальной, если стоит `update-docs`
